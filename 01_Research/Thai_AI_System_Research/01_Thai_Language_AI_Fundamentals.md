# 01 — พื้นฐาน AI ภาษาไทย (Thai Language AI Fundamentals)

> วันที่ตรวจสอบข้อมูล: 21 กรกฎาคม 2026

ไฟล์นี้อธิบายว่า **ทำไมภาษาไทยจึงยากสำหรับ AI** และมีผลต่อการออกแบบ RAG อย่างไร แยก "ข้อเท็จจริง" กับ "ข้อเสนอแนะ" ให้ชัด

## 1. การตัดคำภาษาไทย (Word Segmentation) และการไม่มีช่องว่างระหว่างคำ

> ข้อเท็จจริง: ภาษาไทยเขียนติดกันไม่มีช่องว่างแยกคำ (unsegmented/scriptio continua) เช่น `ตากลม` ตัดได้ทั้ง "ตา-กลม" และ "ตาก-ลม" การตัดคำจึงเป็นปัญหาที่มีความกำกวมโดยธรรมชาติ

ผลกระทบต่อระบบ:
- **BM25 / keyword search** ต้องตัดคำก่อน ถ้าตัดผิด → ค้นไม่เจอ
- **Tokenizer ของโมเดลหลายภาษา** มักแบ่งไทยเป็น subword/ไบต์ ทำให้ 1 คำไทยกินหลาย token → เปลือง context และช้าลง
- **การนับความยาว chunk** ต้องระวัง เพราะจำนวนตัวอักษร ≠ จำนวน token

**เครื่องมือตัดคำ (เปรียบเทียบ):**

| เครื่องมือ | วิธีการ | ข้อดี | ข้อเสีย/ข้อจำกัด | เหมาะกับกรณีใด |
|-----------|---------|-------|-----------------|----------------|
| PyThaiNLP `newmm` | dictionary + maximal matching (TCC) | เร็วมาก, เป็น default, ติดตั้งง่าย | คุณภาพต่ำกว่าโมเดล deep ในคำใหม่/กำกวม | งานทั่วไป, throughput สูง |
| `deepcut` | CNN บน character | แม่นสูง (SOTA เดิม) | ช้ากว่ามาก, ต้องพึ่ง TensorFlow | งานที่เน้นความแม่น ปริมาณไม่มาก |
| `attacut` | CNN เบา | เร็วกว่า deepcut, แม่นใกล้เคียง | ต้องติดตั้งเพิ่ม | สมดุลความเร็ว/ความแม่น |
| PyThaiNLP `nercut`/`icu`(pyicu) | rule/ICU | สำรอง, ใช้ได้หลายภาษา | ความแม่นไทยไม่เท่าตัวข้างต้น | fallback |

> อ้างอิง: PyThaiNLP tokenize docs และ AttaCut survey (ดู `16_...`). newmm เป็น default ของ `word_tokenize` และใช้ dictionary + Thai Character Cluster (TCC)

> **ข้อเสนอแนะ:** สำหรับ RAG ภาษาไทย ใช้ `newmm` เป็นค่าเริ่มต้นสำหรับ hybrid/BM25 เพราะเร็วและเสถียร แล้วค่อยพิจารณา `attacut`/`deepcut` ถ้าพบว่าการค้นพลาดเพราะตัดคำผิด

## 2. คำย่อ ภาษาพูด คำทับศัพท์ และทางการ vs ไม่ทางการ

- **คำย่อ/อักษรย่อ**: "รร." (โรงเรียน/โรงแรม), "จนท.", "พ.ร.บ." — กำกวมและขึ้นกับบริบท
- **ภาษาพูด/แชท**: "งง", "จริงดิ", สะกดผิดโดยตั้งใจ, วรรณยุกต์ผิด
- **คำทับศัพท์อังกฤษ**: "คอมพิวเตอร์/computer", "เซิร์ฟเวอร์/server" สะกดได้หลายแบบ
- **ทางการ vs ไม่ทางการ**: เอกสารราชการใช้ภาษาระดับสูง แต่คำถามผู้ใช้มักเป็นภาษาพูด → เกิด **vocabulary gap** ระหว่างคำถามกับเอกสาร

> **ข้อเสนอแนะ:** ใช้ embedding แบบ semantic (ไม่ใช่ keyword ล้วน) เพื่อลด gap นี้ และพิจารณา **query rewriting/expansion** (ให้ LLM เขียนคำถามใหม่ให้เป็นทางการ) ก่อน retrieve

## 3. เอกสารไทยที่มีภาษาอังกฤษปะปน (Code-switching)

เอกสารวิชาการ/เทคนิคไทยมักปนอังกฤษ เช่น "ใช้ neural network ในการ train model" ระบบต้องรองรับการค้นข้าม 2 ภาษาในเอกสารเดียว → เลือก **multilingual embedding** ที่แข็งทั้งไทยและอังกฤษ (ดู `05_...`, เช่น BGE-M3, multilingual-e5)

## 4. OCR ภาษาไทย (เอกสารสแกน)

> ข้อเท็จจริง: OCR ไทยยากกว่าอังกฤษเพราะมีสระ/วรรณยุกต์วางบน-ล่างพยัญชนะ (stacked marks) และไม่มีช่องว่างคำ ทางเลือกหลัก ณ 2026:
> - **Tesseract** (`tha` traineddata) — ฟรี ใช้ง่าย แต่แม่นยำปานกลางกับเอกสารซับซ้อน/ตาราง
> - **PaddleOCR** — รองรับหลายภาษา ผลดีกับ layout
> - **Typhoon OCR (scb-10x)** — Vision-Language Model โอเพนซอร์สเจาะจงเอกสารไทย รองรับ layout/ตาราง คืนผลเป็น markdown/HTML รุ่น 1.5 (พ.ย. 2025) เล็ก/เร็วขึ้น (ดูอ้างอิง arXiv 2601.14722 และ PyPI `typhoon-ocr`)
> - **Cloud OCR** (Google Document AI, Azure AI Document Intelligence) — แม่นสูง แต่ส่งข้อมูลออกนอกองค์กร (พิจารณา privacy)

> **ข้อเสนอแนะ:** เอกสารสแกนภาษาไทยที่มีตาราง/layout ซับซ้อน ให้ทดลอง Typhoon OCR หรือ PaddleOCR ก่อน แล้ววัดผลกับตัวอย่างจริงขององค์กร (ดู `06_...`, `10_...`)

## 5. Tokenization และ Context Window

- โมเดลหลายภาษาที่ไม่ได้ปรับ vocab สำหรับไทยจะใช้ token ต่อคำมากกว่า → **1,000 คำไทยอาจกิน 1,500–3,000+ token** (ค่าประมาณ ขึ้นกับ tokenizer)
- ผลคือ context window ที่ประกาศ (เช่น 8K/128K token) จุ "เนื้อหาไทย" ได้น้อยกว่าที่คิด และ inference ช้าลง/แพงขึ้น
- โมเดลที่เทรนเน้นไทย (เช่น Typhoon, SEA-LION, OpenThaiGPT) มักมี tokenizer ที่ efficient กับไทยกว่า

> **ข้อเสนอแนะ:** วัด "token ต่ออักขระไทย" ของ tokenizer ที่จะใช้จริง ก่อนตั้งขนาด chunk และงบ context

## 6. Hallucination (การแต่งข้อมูล)

โมเดลเล็กมีแนวโน้ม hallucinate สูงเมื่อถูกถามนอกความรู้ RAG ช่วยลดได้ถ้า:
- บังคับให้ตอบจาก context เท่านั้น + สั่งให้ตอบ "ไม่พบข้อมูล" เมื่อไม่มีหลักฐาน
- แนบ citation ทุกครั้ง และวัด **faithfulness / hallucination rate** (ดู `10_...`)

## 7. Semantic Search ภาษาไทย

การค้นเชิงความหมายต้องใช้ embedding ที่เข้าใจไทย ปัญหาที่พบ:
- embedding ที่เทรนอังกฤษล้วนจะแมปคำไทยได้แย่
- คำถามสั้น (query) กับเอกสารยาว (passage) มี distribution ต่างกัน → พิจารณา instruction-style embedding หรือ reranker
- ควรทำ **hybrid search** (semantic + BM25) เพราะไทยมีชื่อเฉพาะ/เลขเอกสารที่ keyword จับได้ดีกว่า (ดู `05_...`)

## 8. สรุปเครื่องมือจัดการข้อความไทย (แนะนำชุดเริ่มต้น)

| งาน | เครื่องมือแนะนำ | หมายเหตุ |

| embedding ไทย | BGE-M3 / multilingual-e5-large | ดู `05_...` |
| การประเมิน | PyThaiNLP utils + RAGAS | ดู `10_...` |
