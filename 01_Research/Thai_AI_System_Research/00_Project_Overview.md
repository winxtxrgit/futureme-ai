# 00 — ภาพรวมโครงการ (Project Overview)

> วันที่ตรวจสอบข้อมูล: 21 กรกฎาคม 2026

## 1. ปัญหาที่ระบบต้องแก้ (Problem Statement)

องค์กร มหาวิทยาลัย และทีมวิจัยในไทยมีเอกสารจำนวนมาก เช่น ระเบียบ คู่มือ งานวิจัย รายงานประจำปี เอกสารสัญญา และฐานข้อมูลภายใน แต่การค้นหาและสรุปข้อมูลเหล่านี้ยังทำด้วยมือ ใช้เวลานาน และพึ่งพาบุคคลที่รู้เรื่องเฉพาะ ปัญหาหลักคือ:

- **ค้นหายาก** — keyword search ทั่วไปไม่เข้าใจความหมาย (semantic) และภาษาไทยไม่มีช่องว่างระหว่างคำ ทำให้ค้นพลาด
- **โมเดล AI ทั่วไป (เช่น chatbot ทั่วไป) ไม่รู้ข้อมูลภายในองค์กร** และมัก"แต่งคำตอบ" (hallucination)
- **ส่งข้อมูลลับออกนอกองค์กรไม่ได้** — ข้อจำกัดด้านความปลอดภัยและ พ.ร.บ.คุ้มครองข้อมูลส่วนบุคคล (PDPA)
- **งบประมาณและฮาร์ดแวร์จำกัด** — ใช้โมเดลใหญ่ระดับหลายร้อยพันล้านพารามิเตอร์บนเครื่องตัวเองไม่ไหว

**เป้าหมายของระบบ:** ผู้ช่วยถาม-ตอบภาษาไทยที่ (ก) ตอบจากเอกสารจริงพร้อมอ้างอิงแหล่งที่มา (citation) (ข) รันบนทรัพยากรจำกัดได้ (ค) ควบคุมข้อมูลไว้ในองค์กรได้

## 2. เหตุผลที่ควรใช้โมเดลขนาดเล็ก (Small Language Model)

> ข้อเท็จจริง (มีอ้างอิงในไฟล์ 02): โมเดลระดับ 1B–9B พารามิเตอร์ที่ผ่านการปรับแต่ง (instruction-tuned) และ quantize แล้ว สามารถทำงานถาม-ตอบเชิงเอกสารได้ดีเมื่อมี RAG ช่วย โดยไม่ต้องใช้ GPU ระดับ data center

- **ต้นทุนต่ำ** — รันบน consumer GPU (เช่น 8–24GB VRAM) หรือแม้แต่ CPU ได้ (ช้าลง)
- **ควบคุมข้อมูลได้** — deploy ในองค์กร (on-premise) ข้อมูลไม่ออกนอกระบบ
- **latency ต่ำ/คุมได้** — ไม่ต้องพึ่ง API ภายนอกที่อาจล่มหรือคิดเงินตามการใช้
- **ปรับแต่งได้** — ใช้ LoRA/QLoRA เทรนบนการ์ดเดียวได้

**ข้อแลกเปลี่ยน (trade-off):** โมเดลเล็กมีความสามารถ reasoning และความรู้ทั่วไปน้อยกว่าโมเดลใหญ่ จึง **ต้องพึ่ง RAG เพื่อชดเชยความรู้เฉพาะทาง** และต้องออกแบบ prompt/pipeline ให้รัดกุม

## 3. บทบาทของ RAG (Retrieval-Augmented Generation)

RAG = ให้โมเดล "เปิดตำราก่อนตอบ" แทนที่จะตอบจากความจำ ระบบจะ (1) ค้นเอกสารที่เกี่ยวข้องกับคำถาม (2) แนบข้อความเหล่านั้นเข้าไปใน prompt (3) ให้โมเดลตอบโดยอ้างอิงเฉพาะข้อมูลที่ให้มา

RAG จึงเป็น **"สมองที่สอง" (second brain)** — เป็นหน่วยความจำภายนอกที่อัปเดตได้ทันทีโดยไม่ต้องเทรนโมเดลใหม่ ลด hallucination และให้ citation ได้

## 4. บทบาทของ Fine-tuning (LoRA/QLoRA)

Fine-tuning = ปรับ "น้ำหนัก" ของโมเดลจากตัวอย่างเพิ่มเติม เหมาะกับการปรับ **รูปแบบ/สไตล์/พฤติกรรม** เช่น ให้ตอบเป็นภาษาราชการไทย ตอบตาม format เฉพาะ หรือทำงานเฉพาะโดเมนที่มีศัพท์เฉพาะมาก LoRA/QLoRA ทำให้ fine-tune ได้ด้วยทรัพยากรน้อย

⚠️ Fine-tuning **ไม่ใช่**วิธีที่ดีในการ "ยัดความรู้/ข้อเท็จจริงใหม่" ที่เปลี่ยนบ่อย — งานนั้นเป็นของ RAG

## 5. ความแตกต่าง: Prompt Engineering vs RAG vs Fine-tuning

| มิติ | Prompt Engineering | RAG | Fine-tuning (LoRA/QLoRA) |
|------|--------------------|-----|--------------------------|
| ทำอะไร | ออกแบบคำสั่ง/ตัวอย่างใน prompt | ดึงเอกสารมาแนบใน prompt | ปรับน้ำหนักโมเดล |
| เหมาะกับ | ปรับพฤติกรรมง่าย ๆ, format | ความรู้เฉพาะทางที่เปลี่ยนได้ | สไตล์/รูปแบบ/โดเมนคงที่ |
| อัปเดตความรู้ | ใส่เองใน prompt (จำกัด) | อัปเดตเอกสารได้ทันที | ต้องเทรนใหม่ |
| ต้นทุนเริ่มต้น | ต่ำสุด | ปานกลาง (ต้องมี vector DB) | สูงกว่า (ต้องเตรียม dataset + GPU) |
| ลด hallucination | น้อย | มาก (ถ้ามี citation) | ปานกลาง |
| ตอบเรื่องนอกข้อมูล | ได้ (เสี่ยงมั่ว) | ปฏิเสธได้ถ้าไม่พบ | เสี่ยงมั่ว |
| **เหมาะกับกรณีใด** | ต้นแบบเร็ว, งานทั่วไป | ถาม-ตอบเอกสารองค์กร | บังคับ format, ศัพท์เฉพาะหนัก |
| **ข้อจำกัด** | คุมความรู้ไม่ได้ | คุณภาพขึ้นกับ retrieval | ข้อมูลเก่าค้างในน้ำหนัก, ต้องระวัง overfit |

> **ข้อเสนอแนะเชิงออกแบบ:** เริ่มจาก **Prompt → RAG → (ถ้ายังไม่พอ) Fine-tuning** ตามลำดับ อย่ากระโดดไป fine-tune ก่อน เพราะ RAG แก้ปัญหา "ไม่รู้ข้อมูลเรา" ได้เกือบทั้งหมดด้วยต้นทุนต่ำกว่า

## 6. ตัวอย่างกรณีใช้งาน (Use Cases)

**มหาวิทยาลัย / งานวิจัย**
- ผู้ช่วยค้นงานวิจัยในคลังวิทยานิพนธ์/บทความ ตอบพร้อมอ้างอิงเล่ม/หน้า
- ตอบคำถามระเบียบการศึกษา ปฏิทินการศึกษา ทุนวิจัย
- สรุปเปเปอร์และเปรียบเทียบวิธีการ

**องค์กร**
- Helpdesk ภายใน (HR, IT, ระเบียบพัสดุ) ตอบจากคู่มือจริง
- ผู้ช่วยฝ่ายกฎหมาย/สัญญา ค้นข้อสัญญาที่เกี่ยวข้อง (มี human approval)
- สรุปรายงาน วิเคราะห์เอกสารการเงิน (พร้อม citation)

## 7. ขอบเขตของโครงการ (Scope)

**อยู่ในขอบเขต:** ระบบถาม-ตอบภาษาไทยจากเอกสารด้วย SLM + RAG, การ ingest เอกสารไทยหลายรูปแบบ, การปรับแต่งด้วย LoRA/QLoRA, การประเมินผล, การออกแบบ infra/security/cost, prototype ที่รันได้

**นอกขอบเขต (ในเอกสารชุดนี้):** การเทรนโมเดลตั้งแต่ศูนย์ (pretraining), งาน multimodal เต็มรูปแบบ (เสียง/วิดีโอ) แม้จะกล่าวถึง OCR, การทำ production ที่รองรับผู้ใช้ระดับล้าน (กล่าวถึงหลักการแต่ไม่ลงลึกทุกส่วน)

## 8. ผลลัพธ์ที่คาดหวัง (Expected Outcomes)

1. เข้าใจภูมิทัศน์เครื่องมือและโมเดลไทย/หลายภาษาที่เป็นปัจจุบัน
2. มีสถาปัตยกรรมอ้างอิง (reference architecture) 3 ระดับ
3. มี prototype RAG ภาษาไทยที่รันได้และมี citation
4. มีแผน roadmap, cost model, และ checklist ความปลอดภัย
5. มีเกณฑ์และชุดข้อสอบสำหรับวัดผลระบบภาษาไทย
