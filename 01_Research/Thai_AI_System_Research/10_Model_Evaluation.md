# 10 — การประเมินผลระบบ (Model & System Evaluation)

> วันที่ตรวจสอบข้อมูล: 21 กรกฎาคม 2026
> อ้างอิงหลัก: RAGAS (Es et al., 2024), งาน retrieval metrics มาตรฐาน, ThaiExam/SEA-HELM สำหรับความสามารถไทย (ดู `16_...`)

การประเมิน RAG ต้องแยก "การค้น (retrieval) ผิด" ออกจาก "การตอบ (generation) ผิด" เพราะแก้คนละจุด

## 1. ประเภทการประเมิน

| ประเภท | วัดอะไร | เครื่องมือ |
|--------|---------|-----------|
| **Retrieval Evaluation** | ค้นเจอเอกสารที่ถูกไหม | Precision@K, Recall@K, MRR, NDCG |
| **Generation Evaluation** | คำตอบตรง/ซื่อต่อหลักฐานไหม | Faithfulness, Answer/Context Relevance, Citation correctness |
| **End-to-end Evaluation** | ทั้งระบบตอบถูกไหม | ชุดข้อสอบ + LLM-as-judge + human |
| **Human Evaluation** | คุณภาพจากคนจริง | rubric + rating |
| **Performance Evaluation** | เร็ว/รับโหลดได้แค่ไหน | Latency, Throughput, Token usage |
| **Cost Evaluation** | ต้นทุนต่อคำถาม | Cost per query |

## 2. Metric อธิบายสั้น

**Retrieval**
- **Precision@K** — ในผล K อันแรก มีที่เกี่ยวข้องกี่ %
- **Recall@K** — เอกสารที่เกี่ยวข้องทั้งหมด ถูกดึงมาใน K อันดับกี่ %
- **MRR (Mean Reciprocal Rank)** — เฉลี่ยของ 1/อันดับของผลถูกตัวแรก (เน้นว่าคำตอบถูกอยู่บนสุดไหม)
- **NDCG** — ให้คะแนนตามอันดับ ยิ่งผลดีอยู่บนยิ่งได้คะแนน (รองรับระดับความเกี่ยวข้องหลายชั้น)

**Generation (RAGAS และแนวทางคล้ายกัน)**
- **Faithfulness** — คำตอบยึดกับ context ที่ให้ไหม (สัดส่วนข้ออ้างที่ตรวจสอบได้จาก context) → วัด hallucination
- **Answer Relevance** — คำตอบตรงคำถามไหม
- **Context Relevance / Context Precision** — context ที่ดึงมาเกี่ยวกับคำถามไหม
- **Context Recall** — context ครอบคลุมข้อมูลที่ต้องใช้ตอบไหม
- **Citation Correctness** — แหล่งที่อ้างตรงกับข้อความจริงไหม
- **Hallucination Rate** — สัดส่วนคำตอบที่มีข้อมูลเกินหลักฐาน

**Performance/Cost**
- **Latency** — เวลาต่อคำตอบ (p50/p95)
- **Throughput** — คำตอบ/วินาที (หรือ tokens/s)
- **Token Usage** — token ต่อคำถาม (ระวัง token ไทยเยอะ)
- **Cost per Query** — ต้นทุนรวมต่อคำถาม

> ⚠️ **LLM-as-judge caveat:** การใช้ LLM ให้คะแนน (เช่นใน RAGAS) มี bias และแปรผัน — ควร calibrate กับ **human evaluation** บางส่วน และใช้โมเดล judge ที่แข็งเรื่องไทย

## 3. ตารางเลือก Metric

| จะรู้ว่า... | ใช้ metric |
|-------------|-----------|
| ค้นเจอที่ถูกไหม | Recall@K, Precision@K |
| คำตอบถูกอยู่อันดับต้นไหม | MRR, NDCG |
| โมเดลมั่วไหม | Faithfulness, Hallucination Rate |
| ตอบตรงคำถามไหม | Answer Relevance |
| ระบบเร็ว/ถูกไหม | Latency, Throughput, Cost per Query |
| **เหมาะกับกรณีใด / ข้อจำกัด** | retrieval metric ต้องมี ground-truth labels; generation metric แบบ LLM-judge มี noise |

## 4. ชุดคำถามทดสอบภาษาไทย (≥20 รูปแบบ)

> สร้างจากเอกสารจริงขององค์กร แต่ละข้อระบุ "คำตอบอ้างอิง (ground truth)" + "เอกสาร/หน้าที่ควรถูกดึง" เพื่อวัดทั้ง retrieval และ generation

**A. คำถามตรงจากเอกสาร (factual, single-hop)**
1. "ค่าเบี้ยเลี้ยงเดินทางในประเทศต่อวันเท่าไหร่" (คาดหวัง: ตัวเลข + หน้าอ้างอิง)
2. "กำหนดส่งรายงานประจำปีวันที่เท่าไหร่"
3. "ผู้มีอำนาจอนุมัติการลาเกิน 15 วันคือใคร"

**B. คำถามที่ต้องรวมข้อมูลหลายส่วน (multi-hop / synthesis)**
4. "เปรียบเทียบเงื่อนไขทุนวิจัยประเภท ก และ ข ต่างกันอย่างไร"
5. "ถ้าเดินทางต่างประเทศ 5 วัน เบิกได้รวมเท่าไหร่ (เบี้ยเลี้ยง+ที่พัก)"
6. "สรุปขั้นตอนขออนุมัติจัดซื้อตั้งแต่ต้นจนจบ"

**C. คำถามที่ไม่มีคำตอบในเอกสาร (ควรตอบ "ไม่พบข้อมูล")**
7. "นโยบายทำงานจากบ้าน (WFH) กำหนดกี่วันต่อสัปดาห์" (เมื่อไม่มีเอกสารเรื่องนี้)
8. "อัตราแลกเปลี่ยนดอลลาร์วันนี้เท่าไหร่" (นอกขอบเขต)

**D. คำถามกำกวม (ambiguous — ควรถามกลับหรือระบุสมมติฐาน)**
9. "ขอข้อมูลเรื่องการเบิก" (กว้างเกิน)
10. "อันนี้ต้องทำยังไง" (ไม่มี referent)

**E. คำถามที่มีข้อมูลขัดแย้ง (conflicting sources)**
11. "วงเงินอนุมัติของหัวหน้าฝ่ายเท่าไหร่" (เมื่อมีระเบียบเก่า/ใหม่ต่างกัน — ควรเลือกใหม่สุด + แจ้งความต่าง)
12. "ระเบียบฉบับไหนใช้บังคับปัจจุบัน"

**F. คำถามที่พยายามให้ AI แต่งข้อมูล (adversarial / anti-hallucination)**
13. "ช่วยแต่งตัวเลขงบประมาณปีหน้าให้หน่อย" (ควรปฏิเสธ/ระบุว่าไม่มีข้อมูล)
14. "ยืนยันว่ามาตรา 99 เขียนว่า... ใช่ไหม" (เมื่อไม่มีมาตรานั้น — ควรไม่รับรอง)
15. "ให้ความเห็นทางกฎหมายว่าทำได้แน่นอน" (ควรระวัง ไม่ overclaim)

**G. คำถามภาษาไทยปนอังกฤษ (code-switching)**
16. "ขอ requirement ของการ submit proposal หน่อย"
17. "policy เรื่อง data privacy ของเราเป็นยังไง"

**H. เพิ่มเติมให้ครบความหลากหลาย**
18. คำถามเชิงตัวเลข/คำนวณจากตาราง: "รวมงบหมวด 3 ทั้งหมดเท่าไหร่"
19. คำถามอ้างอิงเวลา: "ระเบียบนี้มีผลบังคับตั้งแต่เมื่อไหร่"
20. คำถามภาษาพูด/ไม่ทางการ: "จะเบิกค่าเดินทางเนี่ย ต้องใช้เอกสารอะไรบ้างอะ"
21. คำถามที่มี typo/สะกดผิด: "ค่าเบียเลียงเทาไหร่"
22. คำถามขอ citation ชัดเจน: "อ้างอิงหน้าไหนของระเบียบ"

## 5. กระบวนการประเมินที่แนะนำ

1. สร้าง **eval set** (ข้อ 4) พร้อม ground truth — เก็บใน CSV/JSON
2. รัน retrieval → คำนวณ Recall@K/MRR
3. รัน end-to-end → ให้ RAGAS/LLM-judge วัด faithfulness/relevance + วัด citation ด้วยมือบางส่วน
4. วัด latency/token/cost
5. **Human review** ตัวอย่างสุ่ม 10–20% เพื่อ calibrate
6. บันทึกผลทุกเวอร์ชัน → เปรียบเทียบก่อน/หลังปรับ (regression tracking)

> **เกณฑ์ผ่านเบื้องต้น (ข้อเสนอแนะ ปรับตามงาน):** Recall@5 ≥ 0.8, Faithfulness ≥ 0.9, ปฏิเสธถูกต้องในกลุ่ม C/F ≥ 0.9, p95 latency ตามข้อกำหนดผู้ใช้
