# 8 · ข้อเสนอแนะการนำไปใช้

> ส่วนหนึ่งของ [การออกแบบแบบสำรวจปรับตัว](README.md)

**ยังไม่มีการแก้แอปที่ใช้งานอยู่** ตามที่กำหนดไว้ เอกสารนี้บอกว่า *ถ้า* จะลงมือ ควรลงมืออย่างไรและตามลำดับใด

---

## 8.1 สิ่งที่ต้องทำก่อนเขียนโค้ดแม้แต่บรรทัดเดียว

| # | งาน | ทำไมต้องก่อน |
|---|---|---|
| 1 | **จำลองผู้ตอบสังเคราะห์** 5,000 คนผ่านกฎชุดนี้ | หาเส้นทางที่ยาวเกิน 34 สั้นกว่า 18 หรือค้างในสถานะที่ไม่คาด — ถูกกว่าการเจอในห้องเรียนมาก |
| 2 | **IOC จากผู้เชี่ยวชาญ 5 คน** (ครูแนะแนว + นักจิตวิทยาการปรึกษา) | ความตรงเชิงเนื้อหาต้องมาก่อนความเที่ยง เกณฑ์ที่ใช้กันคือ IOC ≥ 0.5 |
| 3 | **ให้ครูแนะแนวให้คะแนน 4 แกนของข้อ `forced-choice`** | ตอนนี้การจับคู่ความพึงปรารถนาเป็นการตัดสินของทีมฝ่ายเดียว |
| 4 | **เขียนพจนานุกรม facet สำหรับ `open-text`** | `OPN-01` ยังทริกเกอร์อะไรไม่ได้เลยถ้าไม่มี |
| 5 | **ทดลองอ่านออกเสียงกับ ม.2 จำนวน 5 คน** | ตรวจว่าข้อภาษาไทยอ่านรู้เรื่องจริง ไม่ใช่รู้เรื่องแค่กับผู้ใหญ่ที่เขียน |

**งานที่ 1 คือชิ้นที่คุ้มค่าที่สุด** เพราะทำได้ทันทีโดยไม่ต้องรอผู้ตอบจริง และมันจะจับบั๊กเชิงตรรกะที่เทสต์หน่วยจับไม่ได้

## 8.2 ลำดับการลงโค้ด

### ระยะ 1 — เอนจินล้วน ไม่แตะ UI

```
lib/assessment/
  types.ts          AssessmentState · Response · Contradiction · BranchStatus
  bank.ts           โหลด items.json + ตรวจ 17 กติกาตอนบูต (fail fast)
  scoring.ts        คะแนนมิติ · กลับค่า reverse · maps ของตัวเลือก
  confidence.ts     coverage × consistency
  contradictions.ts detectContradiction()
  budget.ts         budgetKey · หักงบ · กรองคิว
  select.ts         priority() → ข้อถัดไป
  stop.ts           เกณฑ์หยุดทั้งหมด
  simulate.ts       ผู้ตอบสังเคราะห์ (งานที่ 1 ของ §8.1)
```

**ข้อกำหนดที่ต้องเป็นจริงตั้งแต่วันแรก**

| ข้อกำหนด | ทำอย่างไร |
|---|---|
| ฟังก์ชันทั้งหมดเป็น pure | `nextItem(state) → itemId`, `applyResponse(state, r) → state` — ไม่มี I/O ไม่มี Date.now() ข้างใน |
| ไม่มี LLM ในเส้นทางการเลือกข้อ | `lib/assessment/` **ห้าม** import อะไรจาก `lib/chat/` |
| การหยุดพิสูจน์ได้ | เทสต์ property: สุ่มลำดับคำตอบ 100,000 ชุด ทุกชุดต้องจบใน ≤ 34 ข้อ |
| คลังผิด = บูตไม่ขึ้น | `bank.ts` รันกติกา 17 ข้อตอน import ไม่ใช่ตอนใช้ |

เหตุผลของข้อสอง: ผลิตภัณฑ์นี้มีหลักว่า **เอนจินกฎเป็นผู้ตัดสิน ไม่ใช่ LLM**
การแยกโมดูลทำให้หลักนั้นเป็นสิ่งที่ตรวจได้ด้วย lint ไม่ใช่สิ่งที่ต้องเชื่อ

### ระยะ 2 — ต่อกับผลลัพธ์เดิม

จุดที่ต้องระวังที่สุดคือ **การส่งคะแนนเข้าเอนจินเส้นทางที่มีอยู่**

| ต้องส่ง | ห้ามส่ง |
|---|---|
| คะแนน RIASEC 6 ตัว | `selfEfficacy` |
| `confidence[d]` เป็นสถานะ (`low`/`mid`/`high`) | `confidence` เป็นตัวเลขหรือเปอร์เซ็นต์ |
| `profileConsistency` | `values` เป็นตัวกรอง |
| `experienceGap[d]` เพื่อแสดงข้อเสนอให้ไปลอง | ข้อความ `open-text` ดิบเข้าโมเดล |

ชั้นอื่น (B–G) **ไม่เข้าสูตรเลือกเส้นทาง** เข้าเฉพาะการจัดเรียงและการแสดงผล
ถ้าเผลอส่ง `selfEfficacy` เข้าไป ระบบจะกรองเด็กที่มั่นใจต่ำออกจากทางที่เขาสนใจ ซึ่งเป็นข้อผิดที่รายงานตรวจสอบระบุตรงตัว

### ระยะ 3 — UI

| หน้าจอ | ข้อกำหนด |
|---|---|
| ระหว่างตอบ | ไม่แสดงแถบความคืบหน้าเป็นเปอร์เซ็นต์ เพราะจำนวนข้อไม่คงที่ · ใช้ "ตอบแล้ว 12 ข้อ" กับปุ่ม "พอแล้ว" |
| ข้อที่ `sensitivity ≠ none` | ต้องมีปุ่มข้าม |
| หน้าทบทวน | ผู้เรียนเปิดสาขาที่ปิดไปกลับมาเองได้ (§3.4 ข้อ 5) |
| หน้าผล | ทุกมิติแสดง รวมมิติที่หลักฐานน้อย · ไม่มีเปอร์เซ็นต์ความมั่นใจ · ไม่จัดอันดับเส้นทาง · มีคำชี้แจงว่ายังไม่ผ่านการตรวจสอบ |

**ห้ามใส่แถบเปอร์เซ็นต์** ทั้งที่มันดูดีในการนำเสนอ เพราะ `confidence` เป็นฮิวริสติกของทีม
ตัวเลข 78% ทำให้ผู้ใช้เชื่อว่ามีการวัดที่ไม่มีอยู่จริง

### ระยะ 4 — เก็บข้อมูลและตรวจสอบเครื่องมือ

| ขั้น | ต้องมีผู้ตอบ | ได้อะไร |
|---|---|---|
| IOC | ผู้เชี่ยวชาญ 5 | ความตรงเชิงเนื้อหา |
| Cronbach's α ต่อมิติ | ~200 | ความเที่ยงเชิงความสอดคล้องภายใน |
| EFA/CFA 6 ปัจจัย | ~300–500 | โครงสร้าง 6 มิติมีจริงในกลุ่มไทยหรือไม่ |
| Rasch rating-scale / GRM | ~500 | ค่าความยากของข้อ · เตรียมทางไป CAT |
| ทดสอบซ้ำ | ~100 | ความเสถียรข้ามเวลา |

**ลำดับนี้เปลี่ยนไม่ได้** — คำนวณ α ก่อน CFA อาจได้ค่าสูงจากข้อที่ซ้ำความหมายกัน ซึ่งไม่ใช่ความเที่ยงที่ต้องการ

## 8.3 เรื่อง IRT/CAT ที่ต้องพูดให้ตรง

**สิ่งที่ระบบนี้เป็น** แบบสำรวจปรับตัว **ตามกฎ** (rule-based adaptive)
**สิ่งที่ระบบนี้ไม่ใช่** CAT (computerised adaptive testing)

| ต้องมีก่อนจึงจะเรียก CAT ได้ | มีแล้วหรือยัง |
|---|---|
| พารามิเตอร์ข้อที่ปรับเทียบจากข้อมูลจริง | ✗ |
| แบบจำลองที่เหมาะกับข้อมูลจัดอันดับ (GRM/GPCM หรือ Rasch rating-scale) | ✗ |
| ค่าประมาณ θ พร้อมความคลาดเคลื่อนมาตรฐาน | ✗ |
| กฎหยุดที่อ้างอิง SEM ไม่ใช่ฮิวริสติก | ✗ |

**2PL ใช้กับสเกล 5 ระดับไม่ได้** — เป็นแบบจำลองสำหรับข้อสองตัวเลือก
รายงานตรวจสอบของทีมระบุข้อนี้ไว้แล้ว และเอกสารชุดนี้ยึดตาม

เมื่อถึงวันที่มีพารามิเตอร์แล้ว จุดที่ต้องเปลี่ยนคือ `confidence.ts` และ `select.ts` เท่านั้น
ส่วน `budget.ts` `stop.ts` และกฎการปิด/เปิดสาขายังใช้ได้เหมือนเดิม
เพราะมันแก้ปัญหาที่ IRT ไม่ได้แก้: **การไม่ตัดทางเลือกของเด็กเร็วเกินไป**

## 8.4 ความเสี่ยงที่ต้องเฝ้า

| ความเสี่ยง | สัญญาณเตือน | ทำอะไร |
|---|---|---|
| ค่าคงที่กลายเป็นความจริง | มีคนอ้าง "ความมั่นใจ 0.75" ในเอกสารนำเสนอ | เขียนกำกับทุกที่ว่าเป็นค่าที่ทีมตั้ง |
| ข้อกลับด้านวัดคนละมิติ | CFA แสดงการโหลดข้ามปัจจัย | ข้อที่ติด `reviewFlags` อยู่แล้ว 4 ข้อ — ตัดออกได้ ไม่ต้องดัดให้เข้า |
| คลังโตแบบไม่มีทิศทาง | มีคนเพิ่มข้อเพราะ "อยากมีเยอะ" | กติกา 8–10 ใน SCHEMA บังคับสัดส่วน ไม่ใช่จำนวน |
| ผลถูกใช้เป็นคำตัดสิน | ครูหรือผู้ปกครองใช้ผลนี้ห้ามเด็กเลือกทาง | คำชี้แจงต้องอยู่บนหน้าผล ไม่ใช่ใน footer |
| LLM ค่อย ๆ เข้ามาเลือกข้อ | มี import จาก `lib/chat/` ใน `lib/assessment/` | เทสต์ที่ห้าม import ข้ามโมดูล |

## 8.5 สิ่งที่จะเปลี่ยนในแอปเมื่อถึงเวลา — และสิ่งที่จะไม่เปลี่ยน

**เปลี่ยน**
- `data/questions.json` → คลังใหม่ (30 ข้อเดิมยังอยู่ ไม่มีข้อไหนถูกทิ้ง)
- ลำดับข้อจากคงที่ → เลือกตามสถานะ
- คะแนนจากผลรวมตรง → รวมน้ำหนักตาม `diagnosticWeight` และกลับค่า `reverse`

**ไม่เปลี่ยน**
- เอนจินกฎยังเป็นผู้ตัดสินเส้นทาง
- ไม่จัดอันดับเส้นทาง
- ปฏิเสธดีกว่าเดา — ตอนนี้ใช้กับผลแบบสำรวจด้วย (§7.3)
- ข้อความชี้แจงว่าเครื่องมือยังไม่ผ่านการตรวจสอบ

สามข้อหลังนี้คือเหตุผลที่งานทั้งชุดนี้ออกแบบมาแบบนี้
แบบสำรวจที่ยาวขึ้น ฉลาดขึ้น แต่กล้าฟันธงกับเด็กที่ระบบยังไม่รู้จัก จะแย่กว่าแบบสำรวจ 30 ข้อที่มีอยู่
